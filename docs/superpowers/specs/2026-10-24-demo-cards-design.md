# 演示卡设计

日期：2026-10-24
状态：待用户审阅

## 1. 为什么要做

用户要给客户现场演示产品。用户站在旁边讲，test worker 在用户前台的 Chrome 里按事先写好的脚本，自动把线上页面从头到尾操作一遍。用户按 worker 的操作顺序来讲，不需要按「下一步」。

同一段演示要能反复演示。每次演示中发现的问题（页面加载慢、按钮要先展开才能点……）要沉淀下来，下次演示、或换了一个新的 test worker 也能直接用上。

## 2. 目标、非目标、反目标

**目标**
- leader 能建「演示需求」和其中的「演示卡」，演示卡指向仓库里的一份演示脚本文件。
- 用户在看板上点「开始演示」，一个空闲的 test worker 领走并在前台浏览器按脚本顺序执行。
- 演示卡可以无限次重复演示；每次演示的结果记在卡的时间线里。
- worker 演示结束后直接把经验写进脚本文件的「经验」部分并提交，不需要人确认。
- 演示期间整个团队不派发开发任务；用户可以随时在看板上叫停。
- 看板上能看到演示进行到第几步、这一步在做什么。

**非目标**
- 不做「下一步」式的逐步控制、不做旁白字幕。
- 不做录屏、截图存档。
- 不做定时演示、无人值守演示。
- 不自动生成脚本：脚本由用户和 leader 商量后 leader 写。

**反目标（做出来但这样就算失败）**
- 演示过程中有人在改线上代码或部署，导致页面中途变化。
- 客户面前 worker 停下来提问、或报错退出、卡住不动。
- worker 写经验时改掉了演示步骤本身，演示内容被悄悄改变。
- 演示卡混进普通需求的统计：通过率、review 次数、「需求完成」判定、审卡队列。

## 3. 用户已定下的事

| 事项 | 决定 |
|---|---|
| 演示方式 | 顺序自动执行，不按下一步；用户在旁讲解 |
| 演示数据 | 演示会造数据。每份数据保留还是清理，由用户和 leader 写脚本时决定，写在脚本里 |
| 经验 | worker 直接写，不需要确认；用户想改演示内容就跟 leader 说 |
| 开始条件 | 只有没有开发任务在进行时才能开始；演示期间不允许改代码 |
| 叫停 | 用户可以随时在看板上叫停 |
| 实现方式 | A + C：演示卡是一种新的卡类型，管流程；脚本和经验是仓库里的文件 |
| 经验提交时机 | 演示结束（跑完或叫停）、冻结解除之后，worker 写经验，服务只提交这一个脚本文件 |

## 4. 考虑过的做法

- **A. 演示卡作为一种新卡类型**：演示卡有自己的循环（待演示 → 演示中 → 收尾 → 待演示），开始检查、冻结、叫停都在服务端。改动最大，但规则都落在一处。
- **B. 演示模板，每次复制出一张普通卡**：复用现有流程，但每演示一次看板多一张卡，自动通过、经验写回模板都要绕路，冻结和叫停照样要另做。
- **C. 脚本和经验放在仓库文件里**：可以在编辑器里改、有 git 历史，但单靠它无法管流程。

**用户选了 A + C**：A 管流程和状态，C 管内容。经验在冻结解除后提交，解决了「演示时不能改仓库」和「经验要写进仓库文件」的冲突。

## 5. 设计

### 5.1 演示需求与演示卡

- 需求多一个标记 `demo: true`（演示需求）。用 `ateam job new "<标题>" --demo` 建。演示需求里只能放演示卡，普通需求里不能放演示卡。
- 演示卡是任务，多一个 `kind: 'demo'` 和 `script`（脚本文件路径，相对项目根，比如 `docs/demo/protocol-adapter.md`）。
  - 用 `ateam demo add --job J5 --title "协议适配全流程" --script docs/demo/protocol-adapter.md [--role test]` 建，角色默认 `test`。
  - 任务的 `paths` 就是 `[script]`，提交经验时只提交这个文件。
  - 脚本文件必须已存在（leader 先写好并自己提交，再建卡）；不存在就报错。
- 演示需求不走「全部通过 → 汇报 → 验收」的流程：没有汇报、不出现在「待你验收」，看板需求列表里显示「演示」标记，不显示进度条百分比。
- 演示卡不进审卡队列，不计入已通过数量、review 次数、一次通过率。

### 5.2 脚本文件格式

Markdown，固定四段，leader 按这个格式写：

```markdown
# 演示：协议适配全流程

## 准备
- 线上地址、要用的测试账号（口令不写在这里，见项目约定）
- 演示前的状态检查，比如「装备列表里不应有『演示-』开头的装备，有就先删掉」

## 演示步骤
1. 打开装备列表页，停 3 秒。（讲：装备登记入口）
2. 新建装备「演示-雷达 {时间}」……停 5 秒。【数据：保留】
3. ……【数据：清理】

## 清理
- 删除名称以「演示-」开头、标了【清理】的数据

## 经验
<!-- worker 维护。只记怎么操作更稳，不改上面的步骤 -->
- 装备列表首次加载约 3 秒，等表格出现再点
```

约定：
- 每步写清做什么、停多久（秒）；造数据的步骤标【数据：保留】或【数据：清理】。
- 演示造的数据统一用「演示-」前缀，名称里可以带 `{时间}`，worker 替换成当前时间，避免第二次演示时重名。
- 「准备」「演示步骤」「清理」由 leader 写；「经验」由 worker 写。

### 5.3 演示卡的状态

演示卡不用普通任务的 pending / working / submitted / approved，用自己的三个状态：

```
ready（待演示）──用户点开始──▶ demoing（演示中）──跑完 / 用户叫停──▶ wrapping（收尾）──worker 提交经验──▶ ready
```

- **ready**：可以开始。卡上显示上次演示的时间和结果。
- **demoing**：worker 在前台浏览器演示中。这时全队冻结派发（见 5.5）。
- **wrapping**：演示已结束，冻结已解除。worker 执行「清理」段（如果这次是跑完的），然后写经验、提交。提交后回到 ready。
- 演示卡也能被 leader 作废（`ateam cancel`），和普通卡一样。

### 5.4 开始演示

看板上演示卡的「开始演示」按钮，满足以下条件才可点，否则置灰并说明原因：

1. 没有任何普通任务处于进行中、返工中、等待答复、待 review（`working` / `asking` / `submitted`）。待领取、已挂起不影响。
2. 没有别的演示卡处于 demoing 或 wrapping。同一时间只演示一张。
3. 有一个在线、手上没有任务、角色和卡一致的 worker。

点了之后（`POST /api/demo/start`），服务端再按同样的条件检查一遍，通过就把卡设为「已请求开始」，冻结立即生效。
- 第一个来 `ateam wait` 的同角色空闲 worker 领到它，卡变为 demoing，worker 收到 `# 演示`。
- 用户也可以像普通卡一样在卡上指派某个 worker，那就只等它来领。
- 如果 2 分钟内没人领，撤回开始请求、解除冻结，看板提示「没有 worker 来领，请确认 test 窗口还在」。

### 5.5 冻结

从开始演示请求生效，到演示结束（跑完或叫停）为止：

- 任何 worker 的 `ateam wait` 都领不到普通任务。worker 照常收到「暂无任务」，提示里写「正在演示，演示结束后继续派发」。
- 已经在手上的任务不受影响（按 5.4 的条件，开始时本来就没有在做的任务）。
- leader 可以继续建需求、加卡、改卡，只是不会派发出去。
- 看板顶部显示一条横幅「演示中：<卡标题>，派发已暂停」，带「停止演示」按钮。

wrapping 阶段不冻结：worker 只是在提交一个文档文件，不影响线上。

### 5.6 演示过程中的 worker

worker 收到 `# 演示`，内容包含：卡标题、脚本路径、脚本全文（服务端读文件附上）、演示规则。worker 照下面的规则执行：

- 先按「准备」段检查状态，再从第 1 步开始顺序执行，每步之间按脚本停留；先读「经验」段，照着经验操作。
- 浏览器必须在前台、用户看得见（遵守项目和用户的浏览器规则）。
- **不提问**（演示中 `ateam ask` 直接报错）。遇到小问题（页面慢、弹窗挡住）自己处理后继续；真走不下去就跳过这一步，记下来，继续下一步。
- 每开始一步报一次：`ateam demo step --as <编号> <第几步>/<总步数> "<这一步做什么>"`。这同时是心跳；看板显示当前步。
- 每次 `demo step` 都会检查用户是否叫停；叫停了就返回 `# 演示已叫停`，worker 立刻停手，停在当前页面，不执行清理。
- 全部跑完：`ateam demo end --as <编号> "<这次的结果：哪些步顺利，哪些跳过、为什么>"`。卡变为 wrapping，冻结解除。

### 5.7 收尾：清理和经验

卡进入 wrapping 后，worker 收到的下一条指令是 `# 演示收尾`：

1. 如果这次是跑完的：执行脚本的「清理」段，只删「演示-」前缀且标了【清理】的数据。叫停的不清理，残留交给下次演示的「准备」段处理。
2. 把这次的经验追加到脚本的「经验」段：只记怎么操作更稳；已有的同类经验就更新那一条，不要重复记。不改「准备」「演示步骤」「清理」三段。
3. `ateam demo save --as <编号> "<记了哪些经验>"`：服务只提交这个脚本文件，提交信息 `[T12] 演示经验：<总结>`。没有新经验时加 `--no-changes`。
4. 卡回到 ready，worker 回到 `ateam wait`。

服务端校验：`demo save` 提交前对比文件，「经验」段以外有改动就拒绝，提示 worker 只改「经验」段。

### 5.8 叫停

- 看板横幅和卡详情里都有「停止演示」（`POST /api/demo/stop`），只在 demoing 时可点。
- 点了之后卡立即记为「已叫停」、冻结立即解除；worker 在下一次 `ateam demo step` 或 `ateam wait` 时收到 `# 演示已叫停`，然后进入收尾（只写经验，不清理）。
- 还没被 worker 领走就叫停：直接撤回开始请求，卡回到 ready。

### 5.8.1 演示中 worker 掉线

- demoing 阶段 worker 长时间没有 `demo step`（按现有租约判定）：卡记为「中断」，冻结解除，卡直接回到 ready，不进入收尾（没人收尾）。看板提示用户。
- wrapping 阶段 worker 掉线：卡回到 ready，这次的经验丢弃（文件里没提交的改动由下一个领到收尾的人看到，见下一条）。
- 简化起见，收尾不转交给别的 worker；下次演示的 worker 在「准备」时 `git status` 看到脚本文件有未提交的改动，按经验段规则保留有用的内容。

### 5.9 看板

- 需求列表里演示需求带「演示」标记。
- 打开演示需求时不显示七列看板，而是演示卡列表。每张卡显示：标题、脚本路径、状态、上次演示的时间和结果、演示次数，以及「开始演示」或「停止演示」按钮。
- 演示中的卡显示当前步「第 3/12 步：新建装备」，以及已经演示了多久。
- 卡详情：脚本路径、指派给、演示历史（每次的开始时间、谁演示的、跑完 / 叫停 / 跳过了哪些步、提交号）。
- 「开始演示」置灰时，悬停提示写明缺什么，比如「T130 进行中，完成后才能演示」「没有空闲的 test worker」。

### 5.10 leader 怎么用（ateam-lead skill 增补）

- 用户说「做一个演示卡」：先和用户一起定演示步骤、每步停留、每份数据保留还是清理；按 5.2 格式写到 `docs/demo/<名字>.md` 并自己提交；然后 `ateam job new --demo`，再 `ateam demo add`。
- 用户想调整演示内容：leader 改脚本的「准备」「演示步骤」「清理」段并提交。卡在 ready 时随时可以改；演示中或收尾中不要改。
- 演示相关事件（`demo_started` / `demo_step` 不通知 / `demo_ended` / `demo_stopped` / `demo_saved`）只需了解，不用 review、不用汇报。

### 5.11 命令汇总

| 命令 | 谁用 | 作用 |
|---|---|---|
| `ateam job new "<标题>" --demo` | leader | 建演示需求 |
| `ateam demo add --job J --title "…" --script <路径> [--role test]` | leader | 建演示卡 |
| `ateam demo step --as <编号> <n>/<总数> "<说明>"` | worker | 报当前步；顺带检查是否叫停 |
| `ateam demo end --as <编号> "<结果>"` | worker | 演示跑完 |
| `ateam demo save --as <编号> "<经验总结>" [--no-changes]` | worker | 提交经验，回到 ready |
| `POST /api/demo/start`、`POST /api/demo/stop` | 看板 | 开始、叫停 |

## 6. 约束

- 沿用项目约定：零依赖、ESM、Node ≥ 18；不新写测试代码，用 scratchpad 一次性探测脚本验证；不做浏览器 UI 验证，看板交给用户手工核对。
- 状态文件里已有的任务、需求不能因为新字段失效：老数据没有 `kind`、`demo`，按普通卡、普通需求处理。
- 只有 `demo save` 会因为演示往仓库提交，且只提交脚本文件。

## 7. 留给实现者决定的

- 状态名、事件名、API 路径的具体写法（以上是建议）。
- 「经验段以外有没有改动」的比对方式。
- 看板演示卡列表的具体布局，沿用现有卡片、抽屉的样式。
- 开始请求无人领的超时（建议 2 分钟），是否做成设置项。

## 8. 我替用户做的决定（请审阅时确认）

- 叫停后**不执行清理**，残留留给下次演示的「准备」段处理（理由：叫停时客户可能还在看，不在客户面前删数据）。
- 演示中 `ateam ask` 直接报错，强制 worker 自己处理或跳过。
- wrapping 阶段不冻结派发。
- 开始演示后 2 分钟没人领就自动撤回。
- 演示需求里不能混放普通卡，普通需求里不能放演示卡。
- 服务端拒绝「经验」段以外的改动，而不是只靠 skill 约束 worker。
