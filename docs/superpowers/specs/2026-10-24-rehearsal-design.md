# 演播卡：预演与快速演播设计

日期：2026-10-24
状态：待用户审阅
前置：`2026-10-24-demo-cards-design.md`（演示卡），本文在它的基础上修改。

## 1. 为什么要改

演示卡第一次上线后发现：worker 演示时每一步都要截图、找元素、想办法，非常慢，不能当着客户这样演。

用户的想法：
- **第一遍叫预演**，不对客户，慢慢走通，把**每一步具体怎么操作**记下来。这份逐步的操作记录才是真正的经验。
- **第二遍起才是演播**，照操作记录顺序执行，只在关键节点核对一下，速度就上来了。

同时把「演示卡」改名为「**演播卡**」。

## 2. 目标、非目标、反目标

**目标**
- 演播卡分预演和演播两种运行。没有可用的操作记录时只能预演。
- 预演产出逐步的操作记录（写在脚本文件里，用户能直接看、能改），并标出关键节点。
- 演播按操作记录快速执行，只在关键节点截图核对。
- 演播遇到对不上的地方，worker 自己切慢档把这一步走通、更新操作记录，尽量把总流程走完；实在走不通才停住。
- 有新代码通过 review 后，演播卡提示「页面可能有变动」，但不强制重新预演。

**非目标**
- 不做不经过大模型的宏式回放（需要确认浏览器工具能执行页面脚本，留到以后）。
- 不做结构化（JSON）操作记录。

**反目标**
- 演播时 worker 仍然每一步都截图、思考，速度没变化。
- 演播中出问题时 worker 停下来提问或卡死不动。
- 操作记录写得太含糊（比如「点保存」），下次照着做还是得重新摸索。

## 3. 用户已定下的事

| 事项 | 决定 |
|---|---|
| 名称 | 演示卡改名演播卡 |
| 两遍 | 第一遍预演（记录怎么操作），第二遍起演播（按记录顺序执行，关键节点核对） |
| 预演中途停下 | 已经走通的步骤也要记下来 |
| 演播出问题 | 加一点智能：先切慢档自己走通，更新记录后继续；走不通才停住 |
| 修正操作记录 | worker 直接改，不需要确认 |
| 代码变了 | 不强制重新预演，标「页面可能有变动」 |
| 操作记录放哪 | 方案 A：写在同一个脚本文件里，用户要能看到 |

## 4. 考虑过的做法

- **A. 操作记录写在脚本文件里，替换原来的「经验」段（用户选择）**：一个文件看全一场演播，用户能读能改；提交和校验逻辑复用。代价是 worker 每次读文字描述再操作，做不到机器回放。
- **B. 结构化 JSON 操作记录**：以后能做宏式回放，但用户看不懂，浏览器工具能力也没确认。用户先选了 B，后改为 A，理由是自己也要看脚本。
- **C. 存在服务里**：不进仓库、没有历史，不满足经验继承。

## 5. 设计

### 5.1 改名

所有面向用户和 worker 的文字：「演示卡 / 演示需求 / 演示」改为「演播卡 / 演播需求 / 演播」，「开始演示」改为「开始演播」。

**为了不打断正在用的数据和习惯，内部名字不改**：命令仍然是 `ateam demo ...`，字段仍是 `kind: 'demo'`、`job.demo`，脚本仍放在 `docs/demo/`。（实现者的决定，见第 8 节。）

### 5.2 脚本格式

原来的「## 经验」段改为「## 操作记录」，其余三段不变：

```markdown
## 演示步骤
1. 打开装备列表页，停 3 秒。
   讲解：这里是装备登记入口……
2. 新建装备「演示-雷达 {时间}」，停 5 秒。【数据：保留】
   讲解：……

## 操作记录
<!-- worker 维护：预演时写，演播时修正。按上面的步骤编号逐条写 -->

### 1. 打开装备列表页
- 打开：https://xxx/equipment
- 等到：表格标题「装备列表」出现（约 3 秒）

### 2. 新建装备 【核对】
- 点右上角蓝色按钮「新建装备」
- 弹窗里「装备名称」输入框填 演示-雷达 {时间}，「类型」下拉选「雷达」
- 点弹窗底部「保存」
- 等到：弹窗关闭，右上角提示「保存成功」
- 核对：列表第一行名称是刚填的名字
```

约定：
- 每个演示步骤对应一条，标题用同样的编号和简述。
- 每条写清：**怎么找到元素**（按钮文字、位置、页面标志）、**做什么**、**等到什么出现才算完成**。
- 关键节点在标题后加【核对】，写一行「核对：……」说明要看到什么。关键节点由 worker 预演时判断，原则是：造数据、跳转页面、提交表单这类「做错了后面全错」的步骤。
- 老脚本里已有的「## 经验」段照样识别为可由 worker 改的段（兼容），预演时 worker 把它整理进操作记录。

服务端校验从「只能改经验段」改为「只能改操作记录段（或旧的经验段）」。

### 5.3 预演和演播

演播卡的运行分两种：

| | 预演 | 演播 |
|---|---|---|
| 谁看 | 用户自己（可以不在旁边） | 客户 |
| 速度 | 慢，每步截图、找元素 | 快，按操作记录直接操作 |
| 截图 | 每步都可以 | 只在【核对】节点 |
| 产出 | 写出完整操作记录 | 修正走不通的步骤 |
| 提词 | 也显示（用户可以顺便练讲解） | 显示 |
| 冻结派发 | 冻结（同样不允许一边改一边跑） | 冻结 |

- 卡上新增标记：
  - **未预演**：从没完整预演过（或操作记录为空）。只能点「开始预演」。
  - **已预演**：最近一次预演跑完。「开始演播」「重新预演」都可以点。
  - **页面可能有变动**：已预演之后又有普通任务通过了 review。两个按钮都能点，演播按钮旁提示「建议先重新预演」。
- 预演跑完就算「已预演」；预演中途停下（叫停、走不通）不算，但已走通的步骤照样写进操作记录，下次预演从头走、可以参考它。
- 运行记录（runs）多一个字段 `mode: 'rehearsal' | 'show'`，看板历史里区分显示。

### 5.4 演播时的两档

worker 收到的演播指令里写明：

1. **快档（默认）**：按操作记录逐条执行，不截图、不做额外判断；只在【核对】步截图对照「核对：」那一行。
2. **慢档**：快档里某一步找不到元素、或【核对】对不上时，只这一步切回预演式做法（截图、找元素、想办法），走通后回到快档继续，并在收尾时把这一步的新做法更新进操作记录。
3. **停住**：慢档也走不通（功能没了、页面报错、数据不对），停在当前页面，`ateam demo end --stuck "<卡在第几步、为什么>"`。这次演播记为「中断」，看板提示用户，卡标为「页面可能有变动」。

`ateam demo step` 增加可选参数 `--slow`：这一步是慢档走通的。看板提词区在慢档步骤上显示一个小标记（用户知道这一步会停顿几秒），运行记录里列出哪些步走了慢档。

### 5.5 收尾

- 预演收尾：完整写出操作记录（跑完的）或已走通部分（中途停的），`ateam demo save`。
- 演播收尾：把走了慢档的步骤的新做法更新进操作记录；没有走慢档就 `--no-changes`。
- 清理规则不变（跑完的才清理）。

### 5.6 「页面可能有变动」

- 每张演播卡记 `rehearsedAt`（最近一次预演跑完的时间）。
- 普通任务通过 review（approve）时，如果时间晚于某张卡的 `rehearsedAt`，那张卡标 `mayChange = true`；重新预演跑完后清除。
- 演播中断（停住）也会标 `mayChange`。

### 5.7 看板

- 演播卡行：标记（未预演 / 已预演 / 页面可能有变动）；按钮「开始预演」，已预演后再加「开始演播」；进行中显示「预演中 / 演播中」。
- 详情抽屉加一块「操作记录」，把脚本里这一段渲染出来给用户看（只读；要改就在编辑器里改文件）。
- 运行记录表加一列「类型」（预演 / 演播），演播行加「慢档步骤」。
- 提词区：慢档步骤显示「慢档」小标记。

### 5.8 leader 和 worker 说明

- leader：脚本模板里「经验」段换成「操作记录」段（留空，worker 写）；建卡后告诉用户「先点开始预演」。
- worker：主循环表和演播规则按预演 / 演播分开写；预演规则重点写「操作记录要写到别人照着就能做的程度」。

## 6. 约束

- 沿用：零依赖、ESM、Node ≥ 18；不新写测试代码，scratchpad 一次性探测；看板交给用户手工核对。
- 老数据兼容：老演示卡没有 `rehearsedAt`，视为未预演；老脚本的「## 经验」段兼容。

## 9. 补充：动作段回放（2026-10-24，用户确认）

问题：第二次演播仍然很慢。原因一：预演没把每步写全，服务端不检查；原因二：大模型每个动作都要截图、思考。

WorkBuddy Browser 工具实测限制：没有执行 JS 的接口；有 `cua_execute` 批量动作（一次最多 100 个，8 种：click、double_click、move、drag、scroll、keypress、type、screenshot），批内没有等待；批内动作引发跳转、弹窗或列表刷新后，后面的动作会静默失效；坐标是视口 CSS px，视口尺寸能从截图结果读到，但不能设置。

- **动作块**：操作记录每一步加一个 ```` ```cua ```` 代码块。内容是一段或多段 JSON 数组，段与段之间用单独一行 `---` 隔开；每段对应一次 `cua_execute` 的 `actions`。会引发跳转、弹窗、列表刷新的动作必须是一段的最后一个。type 里的 `{时间}` 演播时替换。
- **视口**：操作记录开头一行「视口：1694x808」，预演时从截图结果读出。看板显示，演播开始时 worker 截图核对，不一致就 `demo end --stuck` 写明预演时和现在的尺寸。
- **演播**：每段一次 `cua_execute`，不截图；【核对】步把 screenshot 作为下一段的第一个动作放进同一批（最后一步核对单独截一次）。对不上 → 从该段起慢档走通，更新动作块。
- **服务端检查**：预演 `demo end`（跑完）和预演收尾的 `demo save` 时，要求每个演示步骤在操作记录里都有「### N.」条目，并带合法的动作块（JSON 数组、每段 1–100 个、类型在 8 种之内、必填字段齐全）；还要有视口行。不合格就拒绝，列出缺哪几步、哪里不对。预演中途停下（`--stuck`、叫停）不检查。演播收尾的 save 只检查动作块的格式。
- **看板**：步骤大纲每步标「已录 / 未录」；演播卡显示视口尺寸。
