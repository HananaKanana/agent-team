# 项目规则按角色分段

日期：2026-10-25
状态：待用户审阅

## 为什么

项目规则（`.ateam/rules.md`）越来越多，现在每张卡都附上整份规则：前端读到测试的规则，后端读到前端的规则。sp 的 20 条里，全员通用约 4 条，test 专用约 8 条，backend 约 3 条，frontend 约 2 条，frontend 和 test 共用 2 条。

## 用户已定下的事

- 选 A：还是一个文件，用小标题按角色分段；派卡时只附「全员」段和这张卡角色所在的段。
- 没写小标题的规则算「全员」，老项目不用改。
- **leader 用命令行改规则必须经用户确认**，由服务强制检查（沿用 `--user-approved`）。用户自己在看板编辑框里改，不用额外确认。

## 考虑过的做法

- **A. 一个文件、小标题分段（用户选择）**：一条规则可以写在 `## frontend, test` 下面，几个角色共用，不用抄两份；老文件原样可用。
- B. 每个角色一个文件，看板分标签页：最直观，但共用的规则要抄多份，容易改漏。
- C. 每条规则前打 `[test]` 标签：灵活但条数多了看不出结构。

## 设计

### 文件格式

```
- 没有小标题的规则（文件开头）：全员
## ALL
- ……
## backend
- ……
## frontend, test
- ……
```

- 以 `## ` 开头的行开始一段，到下一个 `## ` 行为止。`###` 及更深的标题算段内内容。
- 小标题是 `ALL`（不分大小写；也认 `全员`、`通用`、`所有`）时，这一段发给所有人。不支持空的 `##`：编辑器里看着像漏写了，容易误会；不想写小标题的全员规则直接放在文件开头即可。
- 其他小标题按逗号、顿号、空格拆成角色名，不分大小写，和卡的角色比对（规则同 `sameRole`）。
- 第一个 `## ` 之前的内容算全员。

### 派卡时附什么

- 新领到、接手、继续的卡，以及演播卡（现有 `RULES_KINDS` 不变），按 `task.role` 取：全员内容 + 所有含这个角色的段，保留段标题，按文件里的原顺序拼接。
- 拼出来为空就不附。标题仍写「项目规则（每个任务都必须遵守）」。
- 审卡 worker（critic）现在不收规则，这次不改。

### 命令行

| 命令 | 作用 |
|---|---|
| `ateam rules` | 列出全部规则（原样） |
| `ateam rules --role test` | 预览 test 卡实际收到的内容 |
| `ateam rules add [--role test 或 frontend,test] "<一条规则>" [--user-approved]` | 加一条；不带 `--role` 就加到全员 |
| `ateam rules set --file rules.md [--user-approved]` | 整份替换 |

- **add 落到哪里**：
  - 加到小标题和 `--role` 完全一致的段（比较时忽略角色顺序和大小写）。
  - 没有这样的段，就在文件末尾新建 `## <角色>` 段。
  - 加到全员时：文件里有 ALL 段就加在那一段末尾，否则加在第一个 `## ` 之前。
- **确认**：
  - add 和 set 不带 `--user-approved` 时，服务拒绝（`NEEDS_USER`）并给出要改的内容，让 leader 照抄给用户，用户同意后带上 `--user-approved` 重新运行：
    - add：写明「将在 <段名> 段加一条：<内容>」。
    - set：列出改动前后各段的条数，例如「全员 20 → 4，test 0 → 8，backend 0 → 3……」，并说明「完整新内容见 <文件>」。
  - 带了 `--user-approved` 就直接写入。
- **提醒整理**：`ateam rules` 发现文件没有任何 `## ` 小标题、并且超过 8 条（以 `- ` 开头的行）时，输出末尾提醒：「规则还没按角色分段，各角色都会收到全部规则；可以向用户提议整理（先给用户看分组，确认后 set --user-approved）」。

### 服务

- `GET /api/rules?role=test`：多返回 `forRole`（这个角色收到的内容）。
- `POST /api/rules`：
  - body 加 `userApproved`。
  - 不带时返回 `NEEDS_USER`，带上将要改的说明。
  - 看板保存时带 `userApproved: true`（看板是用户本人在改）。
- `POST /api/rules/add`：body `{ text, role, userApproved }`，落段规则同上，由服务完成，避免命令行和服务各写一套。

### 看板（使用说明 → 项目规则）

- 编辑框不变。
- 编辑框上方的说明补一句小标题写法：「用 `## backend`、`## frontend, test` 分段；不写小标题的算全员」。
- 编辑框下方加「预览：<角色下拉> 会收到」。
  - 下拉选项：全员 + 已出现在小标题里的角色 + 现有卡和 worker 的角色。
  - 选中后，用编辑框里当前的内容（含没保存的修改）在页面上算出这个角色收到的内容，只读显示。
  - 看板里写一份和服务相同的分段解析。

### leader 说明（skill）

- 加规则前先判断给谁，拿不准就放全员；先把「加到哪段、加什么」告诉用户，用户同意后再带 `--user-approved` 运行。
- 整理或挪动已有规则：先把「哪条归哪段」的表给用户看，同意后写好新文件，`set --file … --user-approved`。
- 几个角色都要遵守的规则，写在共用段（`## frontend, test`），不要抄两份。
- 验收后清理需求专用条目那一节照旧，同样需要用户确认。

## 约束

- 零依赖、ESM、Node ≥ 18；不新写测试代码，scratchpad 一次性探测；看板交用户手工核对。
- 规则大小上限 20KB 不变。
- 没有小标题的老文件：每个角色收到的内容和现在一字不差。
